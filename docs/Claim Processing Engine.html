00 · IN ONE PARAGRAPH

A batch job that turns new evidence into versioned beliefs

The engine is a separate, bounded run, the same pattern as ingestion. Something triggers it (new evidence, a rule change, a human correction, a nightly sweep). It works out which claims could be affected, derives or proposes candidate claims, validates them, and compares each one with the current belief. It then writes one of six outcomes: publish, no-op, supersede, dispute, reject or retract. Every write is a new claim version plus a ledger event explaining why. It reads the evidence graph but never writes to it, and it remembers how far it got with a watermark, so a crashed run simply resumes.

Explicit claims: right awayDeterministic rules run on every incremental pass. They are cheap and repeatable.
Inferred claims: in batchesThe model-based proposer runs in the nightly sweep or on request, and only once ADR-002’s policy is accepted.
Corrections: on demandA reviewer’s confirm, dispute or retract runs through the same validate-and-commit path for one claim.

Why split real-time and batch: explicit claims are deterministic and cheap, so they keep pace with ingestion. Model-based proposals cost money and may involve sensitive text, so they run in controlled batches where they can be capped, reviewed and switched off.

03 · STAGES

The pipeline, step by step

Each stage has one job, clear inputs and outputs, and never writes to the evidence graph.

  1. S0
    Plan: work out what could be affected

    Read the watermark and the trigger. Collect the touched artifacts, their one-hop explicit neighbours, and every current claim that cites them. Cap the set at max_items, just as ingestion caps max_pages.

    In: trigger, watermarkOut: impact set (artifact IDs, claim keys)
  2. S1
    Derive explicit claims

    Apply the registry’s deterministic rules to explicit links. For example, a REFERENCES edge from PR #218 to SHOP-142 becomes PR#218 addresses SHOP-142 with status explicit, citing the reference locator.

    In: impact set, registry vNOut: explicit candidates + rule version
  3. S2
    Propose semantic claims (optional)

    Only in batch triggers, and only when enabled. Send the bounded evidence for a subject to the model behind the proposer interface; an offline stub is used in tests. Keep only answers that name a registered predicate and cite evidence IDs from the input.

    In: evidence bundleOut: inferred candidates + model and prompt version + confidence
  4. S3
    Validate

    Check each candidate:

    • the predicate is registered and its endpoints are allowed;
    • every cited evidence ID exists in the graph;
    • the predicate’s evidence minimum is met;
    • valid_from is not earlier than the evidence it rests on;
    • it does not conflict with a current claim.

    Failures carry a reason code.

    In: candidatesOut: valid candidates, rejected candidates with reason, conflict flags
  5. S4
    Reconcile with the current belief

    Look up the current version for the same claim key and choose one of six outcomes using the decision table below. This is the only stage that decides what changes.

    In: valid candidates, current versionsOut: list of write intents
  6. S5
    Commit

    Use one Neo4j transaction per claim key:

    • set superseded_at on the old version;
    • create the new :Claim version with its SUBJECT, OBJECT and CITES edges;
    • append the :ClaimEvent.

    Either all of it lands or none of it does.

    In: write intentsOut: new versions + ledger events
  7. S6
    Summarize and advance

    Move the watermark only past work that committed. Emit a run summary with counts per outcome, versions used, errors and a resume point, in the same shape as the ingestion RunSummary.

    In: commit resultsOut: watermark, claim run summary
04 · DECISIONS

How S4 picks one of six outcomes

A claim key identifies the question a claim answers. For single-valued predicates, such as “why was this PR made”, the key is (subject, predicate). For multi-valued ones, such as “which issues does this PR address”, the object is part of the key too. The registry declares which kind each predicate is.

OutcomeConditionWhat is writtenLedger event
PublishValid, and no current version for the claim keyVersion 1, recorded_at = nowClaimPublished
No-opValid, and its content hash equals the current version’sNothing. The run summary counts it.none
SupersedeSame key, different content, and the new evidence is equal or strongerOld version gets superseded_at = now. New version links SUPERSEDES to the old one.ClaimSuperseded
DisputeConflicts with a current claim, and neither can be ranked above the otherNew versions of both claims with status disputed, linked by CONTRADICTSClaimDisputed
RejectFailed validation in S3A :Claim in lifecycle state rejected with a reason code. Excluded from default retrieval.ClaimRejected
RetractAll cited evidence has been deleted at the source, or a reviewer retracts the claimA new version with status retracted. The previous version is superseded.ClaimRetracted
05 · STATES

The life of one claim

Lifecycle state (where the claim is in the process) is separate from epistemic status (explicit, inferred, disputed or retracted). Terminal states have a heavy border: once there, a claim only ever changes by a new version being added.

06 · EVENTS

The claim ledger

Every change appends one immutable :ClaimEvent. The ledger is the audit trail and the source for “why did our belief change?” queries (FR-14).

Event types
  • TriggerReceived: which trigger, scope and versions
  • ClaimPublished · ClaimSuperseded
  • ClaimDisputed · ClaimRetracted
  • ClaimRejected: with reason code
  • ClaimConfirmed: human review recorded on a new version
  • ReevaluationQueued: picked up by the next sweep
  • RunCompleted: counts, watermark, errors

Every event names its cause (the trigger record and the evidence IDs) and its actor (a rule version, a model version or a named reviewer).

Example event 
{
  "type": "ClaimSuperseded",
  "event_id": "evt_01J…",
  "claim_key": "gh:acme:pr:218|motivated_by",
  "from_version": "v1#9c41…",
  "to_version":   "v2#e07a…",
  "cause": {
    "trigger": "T5 ScheduledSweep 2026-10-20",
    "evidence": ["ci:bench:run:5512",
                 "gh:acme:review:88123"]
  },
  "actor": "proposer model=stub-1 prompt=p3",
  "reason": "stronger_evidence_tier",
  "recorded_at": "2026-10-20T02:04:11Z"
}

08 · GUARANTEES

What holds even when things fail

Evidence untouchedThe engine has no write path to :Artifact or :Actor. AC-8 snapshots the evidence graph before and after a run and compares them.
IdempotentA content hash per version makes replays and rebuilds no-ops. Running a batch twice produces the same claims.
Crash-safeThe watermark moves only past committed work. After a crash, rerun and the engine resumes. Half-written claims cannot exist, because S5 uses one transaction per key.
Boundedmax_items per run, one-hop impact sets, and model calls capped per batch. A partial run reports a resume point.
One writerA single :EngineLock node allows one run at a time, which avoids two runs racing to supersede the same claim.
ExplainableEvery version records the rule, registry or model version and the ledger event that caused it.

Open points to settle before CLM-3
  • T1 needs to detect changed artifacts, not just new ones. Either the writer keeps a last_changed_at when the payload checksum changes, or S0 compares checksums.
  • The evidence tiers per predicate (benchmark > review > PR prose?) belong in the registry and need a decision.
  • The schedule and model-call cap for T5.
