00 · PURPOSE

What this engine does

The Claim Processing Engine is a separate, bounded process. It reads the existing evidence graph, identifies potentially affected claims, derives or proposes candidates, validates them, compares them with current claims, and records the outcome. It does not create or repair artifact-to-artifact relationships in the evidence graph.

Evidence graphExisting Git, Jira, and Slack artifacts and explicit links. Read by the engine; not modified by it.
Claim storeStructured propositions, evidence references, lifecycle state, and version history.
Claim ledgerAn append-only explanation of what changed, why it changed, and which run caused it.

Boundary: ingestion and entity resolution remain responsible for fetching artifacts, identifying them, and creating correct evidence-graph links. Claim processing maintains conclusions derived from that evidence.

02 · STAGE DETAILS

What each stage receives and produces

S0

Plan the impact set

Read the trigger and saved cursor. Identify changed evidence, relevant explicit neighbors, and claims citing that evidence. Bound the number of items processed per run.

Input: trigger, cursor, evidence changes · Output: artifact IDs and claim keys
S1

Derive explicit claims

Apply deterministic rules to known graph relationships. An explicit PR-to-issue reference can yield a claim that the PR references that issue. Keep the source relationship as evidence.

Input: impact set, registry version · Output: normalized candidates and rule metadata
S2

Propose semantic claims — optional

A model may propose meaning not directly encoded as an explicit edge. The proposal must cite evidence IDs from its input and identify model/prompt versions. Model output is not trusted merely because it was generated.

Input: bounded evidence bundle · Output: inferred candidates with provenance
S3

Validate every candidate

Check predicate registration, endpoint types, evidence existence, minimum evidence requirements, and temporal validity. Invalid candidates receive a reason code and cannot be published.

Input: candidates · Output: validated candidates or rejection reasons
S4

Reconcile with the current claim

Find the current version for the claim key. Compare normalized content and evidence. Identical candidates become no-ops; sufficiently supported changes can supersede; unresolved conflicts become disputed.

Input: validated candidates + current versions · Output: write intent or no-op
S5

Commit the outcome

For a change, atomically create the new claim version, update previous-version metadata where appropriate, and append the ledger event. A failed transaction must leave no partial write.

Input: write intent · Output: durable claim version and event
S6

Summarize and advance progress

Report outcome counts, errors, versions, and a resume point. Advance the cursor only past work whose required writes committed successfully.

Input: per-item results · Output: run summary and durable cursor
02A · TRIGGERS

What starts a claim-processing run?

Triggers identify why the engine ran and determine how much work it should perform. For the first PoC, manual execution and ingestion-completed processing are sufficient; later triggers can be added without changing the core pipeline.

TriggerWhen it firesScopeTiming / phase
EvidenceIngestedAn ingestion run completes with new or changed artifacts.Touched artifacts, relevant explicit neighbors, and claims citing them.After ingestion; deterministic claims first.
RulesChangedThe predicate registry or an explicit-claim rule changes.Artifacts matched by the changed rule.On deployment or manual rebuild.
ProposerChangedThe semantic proposer, model, or prompt policy changes.Configured subjects in a bounded batch.Later phase; only when semantic inference is enabled.
HumanCorrectionA reviewer confirms, disputes, or retracts a claim and supplies a reason.One claim key and its affected version history.On demand.
ScheduledSweepA scheduled reevaluation runs.Queued inferred claims and claims whose evidence changed or disappeared.Later phase / batch.
BenchmarkFailureAn evaluation identifies a wrong or missing claim.Claims involved in the failing answer.Later phase; opens a review item rather than silently changing a claim.
AgentHypothesisThe retrieval agent proposes a claim worth investigating.One candidate with cited evidence.Later phase; never auto-promoted without validation.

The original design uses a watermark to track progress. The PoC should also record a run ID and trigger type so each claim change can be traced to the run that caused it.

02B · CLAIM IDENTITY

How does the engine know two candidates are the same claim?

A claim key identifies the proposition being maintained. It must be stable across runs and should not be based on the evidence ID, because different artifacts may support the same proposition.

Single-valued predicate

Use (subject_id, predicate) when only one current value is expected for a subject and predicate.

Example: the primary reason associated with a particular PR.

Multi-valued predicate

Use (subject_id, predicate, object_id) when multiple objects may validly be related to the same subject.

Example: a PR explicitly references several issues.

The predicate registry must declare cardinality. Three concepts must remain distinct: derivation type (explicit or inferred), lifecycle state (candidate, published, disputed, superseded, retracted, rejected), and run outcome (publish, no-op, supersede, dispute, reject, retract).

03 · DECISION RULES

How the engine decides what to do

Reconciliation uses validation, claim identity, current version, and evidence—not a model confidence score alone.

OutcomeDecision conditionWhat is retained
PublishValid candidate; no current claim for this key.New version and ClaimPublished event.
No-opEquivalent normalized content and relevant evidence hash.No new version; count the no-op in the run summary.
SupersedeChanged proposition with evidence ranked sufficiently strong under the predicate policy.New version, lineage to the old version, and ClaimSuperseded event.
DisputeMaterial conflict cannot be reliably ranked.Conflict links, disputed state, and ClaimDisputed event.
RejectCandidate fails validation.Rejected record with reason code; excluded from default retrieval.
RetractReviewer withdraws the claim or supporting evidence is no longer valid.Retraction record and ClaimRetracted event; history remains.

A no-op is a run outcome, not a lifecycle state. Retraction is normally initiated by an existing-claim reevaluation or a reviewer correction—not by comparing two ordinary candidate values. The evidence-ranking policy belongs in the predicate registry. If the engine cannot justify which candidate is stronger, it should dispute rather than guess.

04 · CLAIM LIFECYCLE

States describe the life of a claim version

Lifecycle state and derivation type are separate. A claim can be inferred and published, or inferred and disputed. A published claim can become disputed, superseded, or retracted; a disputed claim may be resolved by a new version or retracted. Rejected candidates never become published without a new validation attempt. Superseded, rejected, and retracted history is retained rather than deleted.

05 · CLAIM + LEDGER OUTPUT

What the system must store

Claim version

  • Stable claim key and version
  • Subject, predicate, and object
  • Evidence IDs and evidence hashes
  • Lifecycle state and derivation type
  • Rule/model/prompt version when relevant
  • Recorded time and reason code

Ledger event

  • Event ID and event type
  • Claim key and affected versions
  • Trigger/run ID and evidence IDs
  • Actor: rule, model, or reviewer
  • Reason for the change
  • Timestamp and outcome

Illustrative event shape:

{
  "type": "ClaimSuperseded",
  "claim_key": "gh:acme:pr:218|motivated_by",
  "from_version": 1,
  "to_version": 2,
  "evidence_ids": ["gh:acme:review:88123"],
  "actor": "explicit-rule-v1",
  "reason": "new_supported_evidence",
  "recorded_at": "..."
}

Example values are illustrative, not data from the deployed application.

06 · FAILURE HANDLING

What happens when a run fails?

SituationExpected behavior
Same evidence is processed againStable key and content hash make the replay a no-op.
Validation failsReject candidate with a reason; continue independent candidates.
Claim write failsRoll back claim version and ledger event together.
Run stops unexpectedlyCursor remains at the last safely committed position; rerun can resume.
Two runs target the same claimSerialize writers or use optimistic version checks.
Source evidence changes or disappearsQueue claims citing it for reevaluation; do not silently erase history.
06A · RELIABILITY GUARANTEES

What must remain true when the engine is rerun or interrupted?

GuaranteeRequired behaviorHow to verify it
Evidence untouchedThe claim engine has no write path to source artifact or actor nodes and their evidence relationships.Snapshot evidence nodes/edges before and after a run and compare.
IdempotentProcessing the same normalized candidate and evidence again does not create a duplicate current claim.Run the same input twice; the second run should produce no-op outcomes.
Crash-safeA claim version and its ledger event commit together; cursor progress never skips uncommitted work.Force a transaction failure and confirm rollback, then rerun.
BoundedEach run caps the number of artifacts, candidates, and optional model calls.Exceed a configured limit and verify a resumable partial-run summary.
Single writerTwo runs cannot race to update the same current claim without coordination.Run concurrent test workers and verify locking or optimistic version checks.
ExplainableEach claim version records its evidence and rule/model version; each change has a reasoned ledger event.Inspect a claim's version history and trace each version to evidence and cause.

These are target guarantees to test, not claims that the current deployed application already provides them.

07 · REVIEW CHECKLIST

How to judge whether the workflow is complete

1

Publish

A valid explicit relationship creates a published claim with traceable evidence.

2

Replay

Processing identical input twice does not create duplicate current claims or duplicate logical changes.

3

Change

New supporting evidence creates a new version when the proposition changes.

4

Conflict

Unresolved conflicting evidence results in a disputed claim, not a guessed answer.

5

Recover

A failed run can resume without skipping uncommitted work or leaving partial writes.

6

Explain

A reviewer can inspect evidence, version history, and ledger events to understand why a claim changed.

Status: This is a proposed workflow design, not a claim that these stages already exist in the deployed SDLC Agent. Incremental ingestion and correct artifact linking remain separate prerequisites.
